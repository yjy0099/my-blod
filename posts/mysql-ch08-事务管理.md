## 一、必须记住的知识点

### 1. 事务是什么

事务用来保证一个业务操作的**完整性**：整个业务**要么全部成功，要么全部失败**，不允许出现「部分成功、部分失败」的中间状态。

最经典的例子是转账：A 扣 100 元、B 加 100 元，这两步必须同生共死，否则钱就不见了或凭空多出来。

```sql
-- 手动控制事务
start transaction;      -- 或 begin
-- ... 一组 DML ...
commit;                 -- 提交
-- 或
rollback;               -- 回滚
```

### 2. 事务的四大特性 ACID

| 特性 | 英文 | 含义 |
| --- | --- | --- |
| 原子性 | Atomicity | 业务操作**不可再分**，要么全做要么全不做 |
| 一致性 | Consistency | 保证操作**前后数据一致**，是事务管理的**最终目的** |
| 隔离性 | Isolation | 多个事务并发时，如何**互相区分、互不干扰** |
| 持久性 | Durability | 提交后的数据**永久存储**到数据库 |

> 记住它们的关系：**原子性是手段，隔离性是并发保障，持久性是结果，一致性是目的**。

### 3. 事务的隔离级别

| 隔离级别 | 英文 | 特点 |
| --- | --- | --- |
| 读未提交 | read uncommitted | 能读到其他事务**未提交**的数据，性能最高、安全性最差 |
| 读已提交 | read committed | 只能读到其他事务**已提交**的数据，Oracle 默认级别 |
| 可重复读 | repeatable read | 同一事务内多次读取同一数据结果一致，**MySQL 默认级别** |
| 序列化读 | serializable | 串行执行，性能最差、最安全 |

```sql
-- 查看当前隔离级别
select @@transaction_isolation;     -- MySQL 8.0
select @@tx_isolation;              -- MySQL 5.7

-- 设置隔离级别
set session transaction isolation level read committed;
```

### 4. 并发问题与隔离级别的对应关系

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | √ | √ | √ |
| 读已提交 | ❌ | √ | √ |
| 可重复读 | ❌ | ❌ | √ |
| 序列化读 | ❌ | ❌ | ❌ |

**三种并发问题的定义：**

- **脏读**：读到了另一个事务**尚未提交**的数据，对方一旦回滚，你读到的就是「脏」数据；
- **不可重复读**：同一事务内**两次读同一行**，结果不同（因为别的事务在中间提交了修改）——针对 `update`/`delete`；
- **幻读**：同一事务内**两次执行同一范围查询**，第二次多出（或少了）一些行（因为别的事务插入/删除了行）——针对 `insert`。

> 隔离级别越高越安全，但并发性能越低。**MySQL 默认「可重复读」，并通过 MVCC + 间隙锁在很大程度上消除了幻读**，这是它与标准定义的一个差异点。

### 5. 隔离性的实现：MVCC 与锁

- **MVCC（多版本并发控制）**：通过为每行数据保留多个版本（`undo log` 链 + 一致性读视图），让「读」不阻塞「写」、「写」不阻塞「读」，从而实现高并发下的可重复读。
- **锁**：
  - 按粒度分：**表锁**（开销小、并发低）、**行锁**（开销大、并发高，InnoDB 支持）；
  - 按性质分：**共享锁 S（读锁）**、**排他锁 X（写锁）**；
  - **间隙锁（Gap Lock）**：锁住一个范围，可重复读下用来防幻读。

## 二、常用命令速查

```sql
start transaction;                     -- 开启事务
commit;                                -- 提交
rollback;                              -- 回滚
savepoint sp1;                         -- 保存点
rollback to sp1;                       -- 回滚到保存点

select @@transaction_isolation;        -- 查隔离级别
set session transaction isolation level repeatable read;
```

## 三、高频面试题（附答案）

**Q1：什么是事务？为什么需要事务？**

事务是一组**不可分割**的数据库操作，保证业务要么全成功、要么全失败。它是为了保证数据的一致性——没有事务，转账扣款成功但入账失败就会导致数据错乱。

**Q2：ACID 分别是什么？哪个是最终目的？**

原子性（不可分割）、一致性（前后数据一致）、隔离性（并发事务互不干扰）、持久性（提交后永久保存）。其中**一致性是最终目的**，其余三者是实现一致性的手段和保障。

**Q3：事务的四种隔离级别？MySQL 默认是哪个？**

读未提交、读已提交、可重复读、序列化。MySQL 默认 **可重复读（repeatable read）**，Oracle 默认读已提交。

**Q4：脏读、不可重复读、幻读分别是什么？**

脏读：读到别人**未提交**的数据；不可重复读：同一事务内两次读**同一行**结果不同（别人改了/删了）；幻读：同一事务内两次读**同一范围**结果行数不同（别人插入了）。三者的危害程度和触发操作都不同。

**Q5：可重复读能解决幻读吗？**

标准定义下不能，但 **MySQL 的 InnoDB 在可重复读级别下通过 MVCC + 间隙锁（Next-Key Lock）基本消除了幻读**，所以实际表现比标准更严格。要注意这是 MySQL 的增强实现。

**Q6：可重复读和读已提交的区别？**

可重复读保证**同一事务内多次读取结果一致**（靠 MVCC 快照）；读已提交每次读取都取**最新已提交**的数据。前者一致性更强，后者并发下更「实时」。

**Q7：什么是 MVCC？**

多版本并发控制。InnoDB 给每行数据维护版本信息（隐藏列 + undo log 版本链），读操作根据事务开始时刻的一致性视图读取**历史版本**，从而做到「读写不阻塞」，既保证可重复读又保持高并发。

**Q8：为什么隔离级别越高性能越差？**

因为隔离性越强，需要的锁或版本控制越严格，事务之间的**并发度越低**：序列化读几乎退化为串行执行；可重复读需要更多间隙锁。这是安全性与性能的权衡。

**Q9：InnoDB 和 MyISAM 在事务上的区别？**

**InnoDB 支持事务和行锁**，有 redo/undo 日志，是默认存储引擎；**MyISAM 不支持事务、只支持表锁**，并发性能差，已被淘汰。选型时基本无脑选 InnoDB。

**Q10：什么是行锁和表锁？**

行锁只锁住操作的行，粒度小、并发高，但开销大、可能死锁（InnoDB 默认）；表锁锁整张表，粒度大、并发低，但开销小、不易死锁。

**Q11：什么情况下行锁会升级为表锁？**

在 InnoDB 中，如果 `where` 条件**没有用到索引**，行锁会退化为**表锁**（因为无法定位到具体行，只能锁全表）。这是「更新语句一定要走索引」的重要原因。

**Q12：事务的持久性靠什么保证？**

靠 **redo log**。事务提交时先写 redo log（WAL，Write-Ahead Logging）再落盘，即使数据库崩溃，重启后也能用 redo log 把已提交的数据重做回来，从而保证持久性。

## 四、易错点

1. **忘记 `commit`**：事务一直挂着不提交，锁不释放，其他会话会被阻塞。
2. **误以为默认隔离级别是「读已提交」**：那是 Oracle 的默认值，MySQL 默认是**可重复读**。
3. **把不可重复读和幻读混为一谈**：前者针对**单行**的修改/删除，后者针对**范围**的插入。
4. **更新条件不走索引导致行锁升级表锁**：并发场景下会大面积阻塞，务必让更新走索引。
5. **以为隔离级别越高越好**：序列化读会严重拖垮并发，按业务需要选即可。
6. **长事务**：事务里做大量操作或包含网络等待，会长时间持有锁、撑大 undo log，应尽量**短小**。
7. **DDL 会隐式提交事务**：执行 `create`/`alter`/`drop`/`truncate` 时，当前事务会被自动提交，前面的操作无法再回滚。
8. **`rollback` 不能撤销 DDL**：`truncate`、`drop` 等在事务里也救不回来。
9. **并发扣库存用「先查后改」**：`select` 出来再 `update` 会超卖，应使用 `update ... set stock = stock - 1 where stock > 0` 的原子写法或加锁。
10. **MVCC 下「读」到旧数据以为是 bug**：可重复读下同一事务内本来就会读到快照数据，需要最新数据要用读已提交或 `for update`。
