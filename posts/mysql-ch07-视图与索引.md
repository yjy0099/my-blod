## 一、必须记住的知识点

### 1. 视图 view

视图是一张**虚表**，是表的映射，本质上是**一条 SQL 查询命令**（不存数据，数据仍在原表）。

两大作用：**① 简化查询命令；② 提高数据安全性**（可只暴露部分列/行给特定用户）。

```sql
create view <viewName> as select ...;

create view v_student_gender as
    select birthday, gender from student
    group by birthday, gender having count(1) > 1;

-- 使用视图就像用表
select * from v_student_gender;

-- 删除视图
drop view <viewName>;
```

### 2. 索引 index

索引用来**提升查询效率**，本质是给字段建立的「目录」，空间换时间。索引基于表中的字段存储。

> **索引不是越多越好**：增、删、改数据时索引都要**重新维护**，索引过多会拖慢写入、占用空间。

### 3. 索引添加原则

- **主键**（天生自带索引）；
- **唯一键**；
- **外键**（关联字段）；
- **经常出现在 `where` 条件上的字段**；
- **字段值重复率低**（区分度高，如手机号；性别这种只有两三个值的字段建索引意义不大）；
- **经常用于排序（`order by`）的字段**。

### 4. 索引类型与语法

| 类型 | 说明 |
| --- | --- |
| 主键索引 | 表中的主键天生自带 |
| 唯一索引 | 唯一约束会自动创建唯一索引 |
| 普通索引 | 手动创建，无唯一性要求 |
| 组合索引 | 多个字段组成一个索引 |

```sql
-- 创建索引（[unique] 可选，代表唯一索引）
create [unique] index <索引名> on <tableName>(字段名, ...);

-- 删除索引
drop index <索引名> on <表名>;

-- 添加主键约束（会同时建立主键索引）
alter table student add constraint primary key(sno);

-- 删除主键约束
alter table tb_student drop primary key;
```

### 5. explain 与 type 等级

```sql
explain select * from student where sno = '202201033333';
```

`explain` 用来查看 SQL 的**执行计划**，重点关注 `type` 列，它表示查询的访问类型。

**性能从好到坏：**

```
system > const > eq_ref > ref > range > index > all
```

- `system` / `const`：常量，最多一行；
- `eq_ref`：连接时用主键/唯一索引，一行匹配一行；
- `ref`：用普通索引匹配多行；
- `range`：范围扫描（`between`、`>`、`<`、`in`）；
- `index`：全索引扫描；
- `all`：**全表扫描**，最差。

> **优化目标：至少达到 `range`，能到 `ref` 更好；出现 `all` 就要考虑加索引。**

### 6. 索引失效的四种情况

- **前模糊查询**：`like '%xxx'`（以 `%` 开头无法走索引，后模糊 `xxx%` 可以）；
- **查询条件发生隐式类型转换**：如字符串字段用数字查（`where phone = 138...` 而 phone 是 varchar）；
- **查询条件字段上使用函数**：如 `where year(create_time) = 2026`，应改成范围查询 `where create_time >= '2026-01-01' and create_time < '2027-01-01'`；
- **组合索引没有遵循最左原则**：组合索引 `(a, b, c)`，查询条件必须从最左列开始连续使用。

### 7. 聚簇索引与非聚簇索引

**聚簇（聚集）索引：**

- 通常由表中的**主键**充当；没有主键则用**第一个唯一键**；
- 数据行的物理存储顺序与索引键顺序一致；
- **一张表只能有一个**（物理顺序只能有一种）；
- 优点：查询效率高、节省存储（叶子节点直接存数据）。

**非聚簇（非聚集）索引：**

- 索引页里存的是**索引键 + 指向数据行的指针**；
- 不影响数据的物理存储顺序；
- **一张表可以有多个**；
- 优点：可建多个、插入更新成本较低。

> **回表**：非聚簇索引查到主键后，还要用主键去聚簇索引里取完整数据行，这次额外查找就叫「回表」。若查询的列全在索引里，则无需回表，称为**覆盖索引**。

### 8. 索引结构：BTree vs B+Tree

| 对比项 | BTree | B+Tree |
| --- | --- | --- |
| 数据存放位置 | 每个节点都存数据 | **只在叶子节点存数据** |
| 查询性能 | 不稳定（离根近的快） | **稳定**（都要到叶子） |
| 范围查找 | 相对困难 | **叶子节点链表，天然适合范围查询** |
| 树高 | 相对高 | 更矮胖，磁盘 IO 更少 |

> MySQL 的 InnoDB 使用 **B+Tree**：非叶子节点只存索引键（不存数据），所以一个节点能容纳更多键、树更矮，磁盘 IO 次数更少；叶子节点用链表相连，范围查询（`between`、`>`）可以顺序扫描，这正是数据库最常用的操作。

## 二、常用命令速查

```sql
-- 视图
create view v as select ...;
drop view v;

-- 索引
create index idx_name on t(col);
create unique index uk_name on t(col);
drop index idx_name on t;

-- 看执行计划
explain select ...;
show index from t;          -- 查看表上的索引
```

## 三、高频面试题（附答案）

**Q1：索引为什么能加快查询？**

索引把「全表逐行扫描」变成「按有序结构快速定位」，类似查字典先看目录。底层 B+Tree 的树高很低（千万级数据通常 3~4 层），每次查询只需几次磁盘 IO，远少于全表扫描。

**Q2：索引是不是越多越好？**

不是。① 每个索引都占存储；② 增删改时要同步维护所有索引，写入变慢；③ 优化器要评估更多执行计划。原则是**按查询需要建索引，优先高频、高区分度的字段**。

**Q3：什么情况下索引会失效？**

① 前模糊 `like '%x'`；② 字段发生**隐式类型转换**（字符串当数字查）；③ 在字段上**用函数或运算**（`where year(t)=2026`、`where id+1=5`）；④ 组合索引**不满足最左原则**；⑤ 使用 `or` 且两侧不都有索引；⑥ 优化器判断全表扫描更快（如数据量极小、区分度极低）。

**Q4：什么是组合索引的「最左原则」？**

组合索引 `(a, b, c)` 只支持从**最左列开始、连续**的查询：`a`、`a+b`、`a+b+c` 能走索引；`b`、`c`、`b+c` 不能。可以理解成「电话簿先按姓排，再按名排」，跳过姓直接找名没法用目录。

**Q5：聚簇索引和非聚簇索引的区别？**

聚簇索引的**叶子节点直接存数据行**，数据物理顺序与索引顺序一致，一张表只能一个（通常是主键）；非聚簇索引叶子节点存的是**主键值/行指针**，需要回表取数据，一张表可建多个。

**Q6：什么是回表？怎么避免？**

非聚簇索引查到主键后，再回聚簇索引取完整行，叫回表。避免方式：**覆盖索引**——让 `select` 的列全部包含在索引中，这样索引里就能拿到所有需要的数据，不用回表。例如 `select a, b from t where a = 1` 且存在索引 `(a, b)`。

**Q7：为什么用 B+Tree 而不是 BTree？**

① B+Tree 非叶子节点不存数据，同样大小的节点能放更多键，**树更矮、IO 更少**；② 数据全在叶子且用链表相连，**范围查询和排序效率高**；③ 查询路径长度一致，**性能稳定**。

**Q8：什么是覆盖索引？**

一个索引包含了查询所需的**所有列**，查询时无需回表。用 `explain` 看 `Extra` 出现 `Using index` 即为覆盖索引，是重要的优化手段。

**Q9：`explain` 关注哪些字段？**

重点看 `type`（访问类型，目标至少 `range`）、`key`（实际使用的索引）、`rows`（预估扫描行数）、`Extra`（`Using filesort`/`Using temporary` 说明有额外排序或临时表，需优化；`Using index` 表示覆盖索引）。

**Q10：`like 'abc%'` 和 `like '%abc'` 哪个能走索引？**

`like 'abc%'`（后模糊）能走索引，因为索引本身按前缀有序；`like '%abc'`（前模糊）不能，因为无法确定从哪开始匹配。同理 `like '%abc%'` 也不能。

**Q11：字符串字段用数字查询为什么会失效？**

因为类型不一致会触发**隐式类型转换**，相当于在字段上套了一个转换函数，索引有序性被破坏，无法使用。应保证传入参数类型与字段一致。

**Q12：视图能更新数据吗？**

简单视图（仅来自单表、无聚合/分组/去重/函数）通常可以更新，会作用到原表；含聚合、`group by`、`distinct`、多表连接等的复杂视图**不可更新**。视图主要用于查询抽象和权限控制。

**Q13：视图和表的区别？**

表**实际存储数据**；视图**不存数据**，只是一条被保存的查询语句，每次查询都动态执行。视图能简化 SQL、隐藏敏感列，但复杂视图会有性能开销。

**Q14：主键索引和唯一索引的区别？**

主键索引**唯一且非空**，一张表只能有一个，且是聚簇索引；唯一索引**唯一但允许 null**（多个 null 不冲突），一张表可以有多个，属于非聚簇索引（若表无主键，第一个唯一索引可被选为聚簇索引）。

## 四、易错点

1. **`like '%x'` 以为能走索引**：前模糊一律失效，能改成后模糊就改。
2. **在索引列上用函数**：`where date(create_time) = '2026-09-21'` 失效，改成范围条件。
3. **隐式类型转换**：`varchar` 字段用数字查、数字字段用字符串查都可能失效。
4. **组合索引顺序建错**：把区分度低的列放最左，或用不到最左列，索引白建。
5. **给低区分度字段建索引**：性别、状态这种只有几个值的字段，索引选择性差，优化器多半不用。
6. **以为索引越多越快**：写入会明显变慢。
7. **`select *` 破坏覆盖索引**：多取一列就可能触发回表。
8. **视图当表用**：视图不存数据，复杂视图每次都要重算，别在热点路径上套多层视图。
9. **`explain` 只看 type 不看 Extra**：`Using filesort`、`Using temporary` 同样是性能信号。
10. **`null` 值的索引**：索引对 `is null` 的支持有限，且含 null 的列在唯一索引下可重复，容易与业务预期不符。
